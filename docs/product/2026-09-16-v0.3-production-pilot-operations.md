# v0.3 Production Pilot Operations

## Purpose

This runbook covers public deployment and pilot evidence for Idea Vending Machine after the deterministic and real-browser v0.3 gates are green.

The deployment evidence levels are intentionally independent. Passing a lower level never implies a higher level.

## Render configuration

Use a dedicated Render Python web service for this repository.

```text
Repository: qwenbe7-ship-it/idea-vending-machine
Branch: main
Runtime: Python
Build command: python -m compileall -q .
Start command: python app.py
Region: Singapore
Pilot plan: Free
Auto deploy: off for the first pilot
HOST=0.0.0.0
```

Do not set `PORT` manually. Render supplies `PORT`, and the application validates it before binding.

The live provider credential is server-owned:

```text
OPENAI_API_KEY
```

Optional server-only overrides remain:

```text
IVM_RESEARCH_MODEL
IVM_REASONING_MODEL
IVM_JUDGE_MODEL
IVM_PROVIDER_TIMEOUT_SECONDS
```

None of these values may be supplied by the browser.

## Health and readiness

`GET /healthz` is passive liveness only. It never calls an external provider.

Expected healthy response:

```json
{"status":"ok"}
```

`GET /readyz` checks only whether server-owned provider configuration is syntactically valid. It does not perform a paid provider call.

Configured:

```json
{"status":"ready","provider":"configured"}
```

Not configured:

```json
{"status":"not_ready","reason":"provider_not_configured"}
```

A deployment may therefore be publicly alive while not yet provider-ready. That state must not be described as a live-provider or production-pilot success.

## Public deployment verifier

Run:

```bash
python scripts/verify_deployment.py https://<service-host>
```

The verifier checks exactly `/healthz` and `/readyz` with bounded network timeouts. Failure output is sanitized and does not print provider-backed response bodies or credentials.

A health-only deployment prints:

```text
PASS: deployment health
NOT READY: provider_not_configured
```

and exits nonzero to prevent it from being mistaken for full readiness.

A configured deployment prints:

```text
PASS: deployment health
PASS: provider configuration readiness
DEPLOYMENT READY WITH EVIDENCE
```

## Evidence labels

### 1. GREEN WITH EVIDENCE

`python scripts/verify.py` passed for the exact commit. This covers compilation, security contracts, unit tests, integration tests, HTTP behavior, runtime contracts, and provider-adapter contracts. It makes no paid provider request.

### 2. BROWSER GREEN WITH EVIDENCE

The exact commit passed `python scripts/verify_browser.py` in real Chromium. The browser gate uses deterministic fake providers and proves the Executive UX, GO/MODIFY approval flow, HOLD/KILL blocking, incomplete/provider-not-configured behavior, ten Reality Cards, and XSS-safe rendering. It receives no live provider credential.

### 3. DEPLOYMENT HEALTH GREEN

The public service responds successfully to `/healthz` with the expected liveness payload. This proves the public process is reachable, not that the AI provider is configured or healthy.

### 4. LIVE PROVIDER GREEN WITH EVIDENCE

In an environment with a valid server-side `OPENAI_API_KEY`, run:

```bash
python scripts/verify_live_provider.py
```

Only a successful real Web Search/source-extraction check plus strict structured-output check earns this label.

### 5. PRODUCTION PILOT GREEN

This is the highest pilot label. It requires all of the following in the deployed environment:

1. `/healthz` is 200 and valid.
2. `/readyz` is 200 and valid.
3. Live provider smoke succeeds.
4. One real business idea completes the deployed `/api/evolve` flow without runtime failure.
5. The result contains exactly ten admitted candidates and ten Reality Assessments.
6. The official project decision is produced only by the deterministic decision engine.
7. Human approval is exercised only when the official decision is GO or MODIFY.
8. Approval produces non-empty `spec.md`, `design.md`, and `plan.md`.

HOLD/KILL remain legitimate business outcomes and must stay blocked from development handoff. Provider/configuration failures remain runtime incomplete/failure states and must never be converted into HOLD/KILL.

## Memory-only assessment limitation

The current `AssessmentStore` is deliberately in-memory, bounded, and expiring. A process restart loses stored assessments and approvals. This is acceptable for the first production pilot but means:

- no durable history across restarts;
- no cross-device recovery;
- no multi-instance shared state;
- an approval must occur before the stored assessment expires or the process restarts.

This limitation must remain visible during the pilot. Do not imply database-backed persistence or SaaS account history.

## Initial pilot sequence

```text
1. Merge exact-head production-readiness PR
2. Confirm main GREEN + Browser GREEN
3. Create dedicated Render service with auto-deploy off
4. Verify public /healthz
5. Verify /readyz
6. If OPENAI_API_KEY is absent, stop at DEPLOYMENT HEALTH GREEN
7. Configure server-owned OPENAI_API_KEY
8. Confirm /readyz
9. Run live-provider smoke
10. Run one real idea through the public evolution flow
11. If GO/MODIFY, explicitly approve and verify all three development documents
12. Record result and only then claim PRODUCTION PILOT GREEN
```

The rule remains: **NO GREEN WITHOUT EVIDENCE**.
