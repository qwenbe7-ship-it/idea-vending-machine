# Idea Vending Machine v0.4 Autonomous Operations

## Purpose

v0.4 changes the primary product path from ChatGPT copy/paste Bridge to server-owned autonomous due diligence:

`idea → research → counter-evidence → ten alternatives → independent judge → deterministic decision → executive report → human approval → spec/design/plan`

ChatGPT Plus Bridge remains available only as an advanced fallback.

## Production process contract

The production process MUST run the v0.4 entrypoint:

```text
python v04_app.py
```

`python app.py` is the v0.3 Bridge-first entrypoint and MUST NOT be treated as an autonomous v0.4 deployment.

## Server-owned provider configuration

The automatic engine reads provider configuration only from trusted server environment variables. The browser never receives or submits credentials.

Required for the autonomous production path:

```text
OPENAI_API_KEY=<server secret>
```

Optional role-model overrides:

```text
OPENAI_RESEARCH_MODEL
OPENAI_REASONING_MODEL
OPENAI_JUDGE_MODEL
OPENAI_TIMEOUT_SECONDS
```

Current default roles are defined by `OpenAIProviderConfig` and must be verified against the provider before changing them. Never place the API key in source control, HTML, browser storage, screenshots, proposals, or user-visible logs.

## Readiness states

### v0.4 with provider configured

Expected `/readyz`:

```json
{
  "status": "ready",
  "default_mode": "autonomous_due_diligence",
  "modes": {
    "autonomous_due_diligence": "ready",
    "chatgpt_plus_bridge": "ready",
    "openai_api": "configured"
  }
}
```

This permits the label `DEPLOYMENT AUTONOMOUS READY WITH EVIDENCE` only after public endpoint verification.

### v0.4 without provider configured

Expected `/readyz`:

```json
{
  "status": "ready",
  "default_mode": "chatgpt_plus_bridge",
  "modes": {
    "autonomous_due_diligence": "not_configured",
    "chatgpt_plus_bridge": "ready",
    "openai_api": "not_configured"
  }
}
```

This state is operational only as a fallback deployment. Do NOT call it autonomous production-ready.

## User experience contract

When autonomous mode is ready, the normal user performs only:

1. Enter idea.
2. Click `자동 분석 시작`.
3. Read the executive result.
4. If decision is GO or MODIFY, explicitly approve the direction before development handoff.

The browser must not ask the user to open ChatGPT, copy a prompt, transfer JSON, choose a model, or supply an API key.

The automatic result must show server-derived execution evidence including evidence count, counter-evidence count, candidate count, independent critique count, and official deterministic decision. Provider/model output cannot set those trusted summary fields.

## Decision trust boundary

- Research/model output is untrusted input.
- Exactly ten candidate families are required by the existing runtime gates.
- Independent evaluation is a separate provider role.
- The provider cannot set the official GO/MODIFY/HOLD/KILL decision.
- The server derives the official decision through existing deterministic gates.
- GO/MODIFY require explicit human approval before spec/design/plan generation.
- HOLD/KILL cannot be approved for development handoff.

## Verification labels

Use only these evidence-backed states:

1. `GREEN WITH EVIDENCE` — Python/unit/integration Production Gate is green on the exact SHA.
2. `BROWSER GREEN WITH EVIDENCE` — real Chromium passes autonomous GO, trusted summary, GO approval, HOLD blocking, missing-provider fallback, and all Bridge regression/security scenarios.
3. `DEPLOYMENT FALLBACK READY WITH EVIDENCE` — v0.4 is public and healthy but autonomous provider is not configured; Bridge fallback is ready.
4. `DEPLOYMENT AUTONOMOUS READY WITH EVIDENCE` — public v0.4 readiness reports autonomous mode ready and server provider configured.
5. `AUTONOMOUS PRODUCTION PILOT GREEN` — a real deployed idea completes the actual provider-backed research → ten alternatives → independent judge → deterministic decision path, and approval behavior is verified.

Never promote state 3 to state 4 or 5 based on code tests alone.

## Deployment procedure

1. Verify exact feature head: Production Gate + Chromium green.
2. Open PR against `main`.
3. Verify PR merge-ref: Production Gate + Chromium green.
4. Squash merge with exact expected head SHA.
5. Verify new exact `main` SHA: Production Gate + Chromium green.
6. Update Render start command to `python v04_app.py`.
7. Keep the API credential server-side only.
8. Trigger Render deploy because autoDeploy is disabled.
9. Confirm the deploy is `live` on the exact new main SHA.
10. Probe `/healthz`, `/readyz`, and root UI using `scripts/verify_deployment.py` plus browser/public checks.
11. Only when readiness says autonomous mode is ready, execute one real production pilot idea.

## Production pilot acceptance

A real pilot must demonstrate all of the following on the deployed service:

- one user idea submitted once;
- external research performed through the live provider path;
- nonzero admissible evidence;
- counter-evidence integrity gate satisfied;
- exactly ten alternatives;
- independent critique coverage;
- server-derived `automation_summary` consistent with the rendered result;
- deterministic GO/MODIFY/HOLD/KILL present only for a completed runtime;
- GO/MODIFY approval produces spec/design/plan;
- HOLD/KILL remains blocked.

If the live provider fails, times out, produces invalid structured output, or does not satisfy research/candidate/judge gates, the pilot is not green. Do not substitute deterministic fixtures for this production-pilot requirement.

## Persistence limitation

`AssessmentStore` and `BridgeStore` remain in-memory bounded stores. A process restart can remove pending runtime/approval/Bridge state. This is acceptable for the controlled v0.4 pilot but not a final multi-instance production architecture. Persistent server-side storage is a later reliability task.

## Rollback

If v0.4 deployment fails before the production pilot:

1. Do not expose a false GO/MODIFY result.
2. Restore the previous known-good service revision or switch the service start command back to `python app.py` only as an explicit v0.3 Bridge rollback.
3. Verify `/healthz` and `/readyz` after rollback.
4. Record that autonomous mode is unavailable; do not label the rollback as v0.4 autonomous-ready.
