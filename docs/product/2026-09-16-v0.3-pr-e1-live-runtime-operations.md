# v0.3 PR E1 — Live Evolution Runtime Operations

## Purpose

PR E1 connects the merged v0.3 A–D contracts into a provider-backed runtime while preserving the rule **NO GREEN WITHOUT EVIDENCE**.

The runtime path is:

```text
raw idea
  -> landscape research
  -> Evidence Graph
  -> assumption/reframe/mechanism/candidate forge
  -> collision research
  -> independent evaluation
  -> deterministic GO / MODIFY / HOLD / KILL
  -> executive report data
```

`POST /api/evolve` is the machine API for this path. The browser may submit only:

```json
{"idea":"..."}
```

Provider configuration, model IDs, system instructions, tools, API credentials, official decisions, and human approval are server-owned and are rejected when supplied by the client.

## E2A ten-candidate Reality Evaluation

E2A strengthens the candidate/evaluation layer without changing the provider trust boundary.

A successful completed E2A run requires:

- exactly **10 trusted candidates**;
- exactly one candidate for each canonical E2A family;
- the strengthened deterministic diversity/admission gate to pass;
- **11 independent critiques** in the completed response: one baseline critique plus ten candidate critiques;
- exactly **10 candidate Reality Assessments** in both the top-level result and Evolution State;
- every Reality Assessment evidence reference to resolve through the registered state evidence and Evidence Graph.

The canonical candidate families are:

```text
adjacent_innovation
category_shift
zero_based_reinvention
axion_automation
prevention_shift_left
outcome_execution
workflow_infrastructure
data_decision_asset
buyer_revenue_inversion
compounding_asset
```

The candidate forge provider request explicitly asks for exactly ten candidates and restricts the provider-facing family schema to this vocabulary. Provider output still cannot create trusted candidate IDs or bypass server-side admission.

### Reality Verdict vs official project decision

Per-candidate Reality Verdicts use a separate vocabulary:

```text
ADVANCE
REVISE
HOLD
REJECT
```

They are **not** the official project-level decision. The official project-level decision remains:

```text
GO
MODIFY
HOLD
KILL
```

Reality Verdicts are derived deterministically from the already-admitted independent critique, feasibility artifact, evidence audit, unresolved collision state, and existing deterministic hard gates. The provider's advisory `recommendation` field does not control the official Reality Verdict.

E2A does not make a second evaluator/provider call to create Reality Assessments. It reuses the independently evaluated critique already produced in the E1 flow, reducing cost and avoiding a second probabilistic decision path.

If the provider returns fewer than ten candidates, duplicates a family, fails diversity/admission, or produces an invalid candidate contract, the runtime must stop as `incomplete`; it must not manufacture missing candidates or emit a false business verdict.

## E2B Executive UX and human approval

E2B makes `/api/evolve` the primary browser flow and keeps trusted decisions server-owned.

A successfully completed evolution result is stored in a bounded in-memory `AssessmentStore` keyed by its trusted `runtime_id`. Default store limits are:

```text
capacity: 32 assessments
TTL: 3600 seconds (1 hour)
```

The store is intentionally memory-only:

- process restart loses all assessments and approvals;
- expired entries cannot be approved;
- entries over capacity evict the oldest record;
- no cross-device history, account system, database, or SaaS persistence is introduced;
- records returned to callers are defensive copies.

Only completed results that still pass runtime, complete-report, and Evidence Graph traceability validation may enter the store. `incomplete` and `failed` results are never stored as approvable assessments.

### Approval endpoint

E2B adds:

```text
POST /api/evolve/approve
```

The browser may send only:

```json
{"runtime_id":"run_..."}
```

The browser cannot send or override `decision`, `confidence`, `selected_concept_id`, `human_decision`, model settings, provider settings, or credentials.

Approval rules are:

1. the runtime ID must resolve to a non-expired server-owned completed assessment;
2. the stored state remains authoritative;
3. only official `GO` or `MODIFY` may proceed;
4. the server sets `human_decision = "proceed"`;
5. the existing `generate_approved_development_package()` handoff creates `spec.md`, `design.md`, and `plan.md`;
6. `HOLD`, `KILL`, `incomplete`, and `failed` cannot create a development package;
7. approval replay is deterministic: once approved, the stored package is returned again rather than regenerated into a divergent result.

The Executive UX renders all ten Reality Cards, including `REJECT` candidates. It renders provider/research text only through safe DOM text operations and uses validated Evidence Graph URLs for external links with `rel="noopener noreferrer"`.

## Runtime truthfulness

Operational failure and business judgment are separate states.

- `completed`: the assessment reached the deterministic decision engine and may contain `GO`, `MODIFY`, `HOLD`, or `KILL`.
- `incomplete`: provider/config/connectivity/schema failure prevented completion. No official business decision is allowed.
- `failed`: internal contract/invariant failure. No official business decision is allowed.

A timeout, auth failure, rate limit, malformed provider response, or missing provider configuration must never be converted into `HOLD` or `KILL`.

## Provider trust boundary

All external provider output is untrusted until existing deterministic validators admit it.

The adapter enforces:

- Web Search for research calls.
- consulted-source extraction from `web_search_call.action.sources`.
- strict JSON-schema structured output for research, ideation, and independent evaluation.
- quarantine of research claims whose URL was not actually consulted.
- no fabricated publication date, geography, market definition, or source metadata.
- closed market-size schema matching the Evidence Graph contract.
- provider response ID, model, usage, and operation recorded as sanitized audit metadata.
- no API key or authorization secret in runtime audit data or normalized exception strings.

Provider output cannot directly set trusted IDs, official verdict, confidence, selected concept, or human approval.

## Deterministic Production Gate

The Production Gate has two deterministic layers and neither calls a paid/live provider.

### Layer 1 — Python/unit/integration gate

Run:

```bash
python scripts/verify.py
```

A successful run proves the repository's compile, security-contract, unit, integration, HTTP, runtime, provider-adapter, and static browser-contract tests for that exact commit.

Evidence label:

```text
DETERMINISTIC CI GREEN
```

### Layer 2 — real Chromium browser gate

CI installs the test-only pinned Playwright dependency and Chromium, then runs:

```bash
python scripts/verify_browser.py
```

The browser verifier uses deterministic fake research/ideation/evaluation providers through the real production HTTP server. It exercises real Chromium for:

- MODIFY and GO approval/handoff;
- HOLD and KILL approval blocking;
- runtime incomplete truthfulness;
- provider-not-configured UI behavior;
- XSS-safe rendering of untrusted idea text;
- ten Reality Cards, ten unique families, expanded ten-dimension detail, and development package previews.

No live provider credential is supplied to this job.

Evidence label:

```text
BROWSER GREEN
```

Browser GREEN proves the deterministic user flow in real Chromium. It does **not** prove live-provider connectivity.

## Opt-in live-provider smoke

In the deployment environment, after setting `OPENAI_API_KEY`, run:

```bash
python scripts/verify_live_provider.py
```

This smoke check uses the same production transport/config/adapter and verifies both:

1. a real Web Search response with consulted-source extraction;
2. a real strict structured-output response.

The script exits nonzero when configuration, connectivity, provider schema, or source extraction fails. Error reporting is sanitized and does not echo provider exception bodies or credentials.

Evidence label:

```text
LIVE PROVIDER GREEN
```

may be claimed only after this live smoke succeeds in the target environment with a valid server-side provider credential.

## Deployment interpretation

The three evidence labels are independent:

```text
DETERMINISTIC CI GREEN
BROWSER GREEN
LIVE PROVIDER GREEN
```

- `DETERMINISTIC CI GREEN`: exact commit passed compile/security/unit/integration contracts.
- `BROWSER GREEN`: exact commit passed the deterministic real-Chromium Executive UX flow.
- `LIVE PROVIDER GREEN`: target environment passed real provider Web Search + structured-output smoke with server-owned credentials.

Do not collapse these labels. In particular, deterministic/browser success must not be described as proof that live provider credentials, networking, or provider behavior are healthy.

## Backward compatibility

The v0.2 endpoints remain available with unchanged semantics:

```text
POST /api/analyze
POST /api/package
```

The v0.3 runtime/approval endpoints are:

```text
POST /api/evolve
POST /api/evolve/approve
```

E2A strengthens the successful `/api/evolve` payload with exact-ten candidate Reality Evaluation data. E2B adds the server-owned approval boundary and Executive UX while reusing the existing v0.2 package generator. It does not add a SaaS account system, payment layer, database, automatic code execution, or browser-controlled provider configuration.
