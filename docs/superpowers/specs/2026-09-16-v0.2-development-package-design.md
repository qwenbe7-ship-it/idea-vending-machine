# Idea Vending Machine v0.2 — Development Package Design

## Goal

Transform one validated idea analysis into a deterministic, internally consistent development package containing `spec.md`, `design.md`, and `plan.md` without calling an external LLM or writing arbitrary files to the server filesystem.

## Scope

v0.2 adds document generation only. It does not add authentication, billing, SaaS operation, external LLM APIs, automatic deployment, or autonomous code execution.

## Architecture

The existing `analyze_idea()` function remains the single source of truth for problem, customer, Agent MD levels, risks, MVP scope, and acceptance criteria. A new pure module, `src/idea_vending/package_generator.py`, consumes the normalized idea plus the analysis object and returns a package dictionary with three Markdown documents.

The HTTP layer adds `POST /api/package`. It validates the request exactly like `/api/analyze`, calls the analyzer, then calls the package generator. The browser UI first shows the v0.1 analysis and then allows the user to generate, preview, and download the three Markdown documents. The server never writes generated project documents to disk.

## Package Contract

`generate_development_package(idea: str, analysis: dict[str, Any]) -> dict[str, str]` returns exactly these keys:

- `spec.md`
- `design.md`
- `plan.md`

All documents must include a stable project identifier derived deterministically from the normalized idea. The same idea and same analysis must always return byte-identical Markdown.

## spec.md

The specification contains the project identifier, original idea, problem statement, target customer, automation and feasibility levels, MVP scope, risks and human-approval constraints, acceptance criteria copied exactly from the analysis object, and an explicit out-of-scope section.

## design.md

The design contains architecture overview, input/processing/output flow, separation of AI judgement from deterministic rules, error and uncertainty handling, security and data-minimization rules, and a verification strategy tied to the acceptance criteria. v0.2 does not invent a future framework or infrastructure stack that is not justified by v0.1.

## plan.md

The plan converts each MVP responsibility into a small implementation task and ends with a Production Gate task. Every task includes a measurable completion condition. The acceptance criteria remain the final release gate.

## API

`POST /api/package` accepts the same JSON shape as `/api/analyze`:

```json
{"idea": "업로드된 영수증에서 항목을 추출하고 표로 정리하는 자동화 도구"}
```

A successful response contains the existing analysis object plus a `documents` object with `spec.md`, `design.md`, and `plan.md`. Invalid input uses the same status codes and error semantics as `/api/analyze`.

## UI

The current single-page UI remains dependency-free. After a successful analysis the user can request a development package. The browser renders document content with text-only DOM APIs and creates local Blob downloads for the three files. Generated Markdown is never injected through `innerHTML`.

## Validation Rules

A package is valid only when:

1. exactly the three required filenames exist;
2. every document is non-empty Markdown;
3. `spec.md` contains every acceptance criterion verbatim;
4. all three documents contain the same deterministic project identifier;
5. no document contains placeholder markers such as `TBD` or `TODO`;
6. repeated calls with the same inputs are byte-identical.

## Testing

Add unit tests for the pure package generator, HTTP tests for `/api/package`, and browser-contract tests that prohibit unsafe HTML insertion and verify the package controls exist. The existing `scripts/verify.py` remains the single Production Gate entry point and must run all tests.

## Success Criteria

v0.2 is complete when a representative idea can move through analysis to three downloadable Markdown documents, all package-contract tests pass, and the GitHub Actions Production Gate is green on the feature branch and after merge.
