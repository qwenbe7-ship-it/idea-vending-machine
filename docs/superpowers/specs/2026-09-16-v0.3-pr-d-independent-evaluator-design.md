# Idea Vending Machine v0.3 PR D — Independent Evaluator & Decision Engine Design

## 1. Purpose

PR D turns the v0.3 candidate pipeline into an independent investment-decision system.

PR C may create and validate evolved candidate concepts, but it intentionally has no authority to select a winner, assign an official score, or set `GO`, `MODIFY`, `HOLD`, or `KILL`. PR D inserts an independent evaluation boundary between Candidate Forge and the executive report.

The governing principle is:

> Generation proposes. Independent evaluation attacks. Deterministic gates decide what the evidence permits.

The evaluator must not inherit the generator's persuasive reasoning or self-scoring. It receives structured candidates, the Evidence Graph, collision-research artifacts, deterministic admission results, and explicit feasibility artifacts. Its output remains untrusted until schema, evidence, and decision gates validate it.

PR D does not build the final Executive UX, live model adapter, persistence/database layer, auth, billing, or SaaS infrastructure. Those remain outside this PR.

---

## 2. Decision Semantics

The four official decisions have exact meanings.

### `GO`

The original idea remains the preferred investment direction.

`GO` is allowed only when:
- the original idea has sufficient problem/economic evidence,
- no material unresolved blocker prevents execution,
- implementation feasibility is acceptable,
- counter-evidence has been considered,
- no evolved candidate demonstrates a sufficiently material structural improvement to justify replacing the original idea.

A `GO` result hands the original idea to the existing v0.2 package flow after explicit human approval.

### `MODIFY`

A materially evolved candidate should replace the raw idea.

`MODIFY` requires:
- one selected evolved candidate with a trusted `candidate_id`,
- that candidate passes all hard gates,
- the candidate improves the opportunity structurally rather than cosmetically,
- the improvement is supported by the normalized evaluation contract,
- the candidate does not introduce an unresolved hard blocker that outweighs the benefit.

A `MODIFY` result must populate `selected_concept_id` and the string-valued `evolved_idea` before downstream handoff. `evolved_idea` is set to the validated candidate's `one_sentence_concept`; the complete candidate object remains in the candidate/evaluation artifacts rather than being inserted into the string field.

### `HOLD`

The opportunity may be attractive, but a material fact is not yet proven or a potentially resolvable dependency/timing issue blocks a responsible investment decision.

Typical causes:
- missing buyer evidence,
- unresolved regulation,
- incomplete collision research,
- material technical dependency uncertainty,
- stale or contradictory evidence,
- insufficient confidence to distinguish `GO`/`MODIFY` from failure,
- multiple evolved finalists that cannot be distinguished with current evidence.

Evidence insufficiency must prefer `HOLD` over false confidence.

### `KILL`

Neither the original idea nor any evolved candidate has sufficient expected value relative to cost/risk, or decisive adverse evidence makes the opportunity unattractive.

`KILL` requires affirmative failure evidence or confirmed hard blockers. Absence of evidence alone is not enough; that condition maps to `HOLD`.

## 3. Architecture

Canonical PR D flow:

```text
PR C Candidate Set
        +
Evidence Graph / Collision Research
        +
Candidate Admission Audit
        +
Original-Idea Baseline
        +
Agent MD / Feasibility Artifacts
                ↓
      Evaluation Request Builder
                ↓
      Independent Evaluator
        (provider-neutral)
                ↓
      Untrusted Evaluation Output
                ↓
      Evaluator Contract Validator
                ↓
      Evidence Reference Validator
                ↓
      Candidate / Baseline Comparison
                ↓
      Deterministic Hard Gates
                ↓
      Decision Engine
                ↓
 GO / MODIFY / HOLD / KILL
                ↓
   Evolution State Update Contract
                ↓
       PR E Executive Report / UX
```

The generator and evaluator are separate logical roles even if the same underlying provider is used during an early implementation. The evaluator request must not contain hidden generator chain-of-thought, generator self-scores, or a preselected winner.

## 4. Inputs

PR D consumes trusted structured artifacts only.

Required inputs:
- `evolution_id`
- preserved `raw_idea`
- normalized intent when available
- Evidence Graph
- candidate list from PR C
- PR C candidate-set admission audit
- collision-research completion state and material unresolved requests
- baseline/original-idea assessment artifact
- candidate-level Agent MD / feasibility artifacts

The official evaluator must reject:
- unknown candidate IDs,
- candidate IDs whose content-addressed ID no longer matches content,
- unknown Evidence Graph claim IDs,
- mismatched `evolution_id`,
- PR C candidate sets that have not passed admission,
- mutated or provider-supplied trusted identifiers.

## 5. Original-Idea Baseline

A crucial PR D requirement is to evaluate the raw idea independently from evolved candidates.

Without an explicit baseline, the system cannot distinguish `GO` (keep the original idea) from `MODIFY` (replace it with an evolved candidate).

The baseline artifact contains:
- `baseline_id` — deterministic content-addressed ID,
- `evolution_id`,
- original problem framing,
- original buyer/user hypothesis,
- original workflow,
- original value-capture hypothesis,
- original automation thesis,
- critical dependencies,
- risks,
- evidence claim references,
- unknowns,
- validation questions.

The baseline is not silently rewritten into an evolved candidate. It preserves the raw idea as the comparison anchor.

## 6. Independent Evaluator Contract

### 6.1 Evaluation dimensions

Each baseline/candidate evaluation uses exactly these ten dimensions:

1. `problem_evidence`
2. `buyer_economics`
3. `structural_differentiation`
4. `competitive_collision`
5. `automation_leverage`
6. `technical_feasibility`
7. `operational_reliability`
8. `regulatory_security_data_risk`
9. `distribution_feasibility`
10. `defensibility_compounding`

Each dimension has a closed assessment vocabulary:
- `strong`
- `mixed`
- `weak`
- `unknown`

No 0–100 score, weighted total, star rating, or pseudo-precise single number is allowed in the official contract.

### 6.2 Per-dimension record

Every dimension assessment contains:
- `dimension`
- `status`
- concise `rationale`
- `supporting_claim_ids`
- `contradicting_claim_ids`
- `material_unknowns`
- `blockers`

All referenced claims must exist in the Evidence Graph. A material factual rationale without a supporting claim must either be represented as an explicit unknown/hypothesis or be rejected by validation.

### 6.3 Candidate critique

Each candidate critique additionally contains:
- `candidate_id`
- strongest reason to pursue
- strongest reason not to pursue
- conditions under which the candidate would become unacceptable
- cheapest next validation if material unknowns remain
- evaluator recommendation vocabulary: `advance`, `revise`, `hold`, or `reject`

This recommendation is advisory only. It does not set the official v0.3 decision.

### 6.4 Baseline critique

The raw-idea baseline uses the same ten dimensions and the same evidence rules. It receives no preferential treatment merely because it came from the user.

---

## 7. Evaluator Trust Boundary

Provider output is untrusted.

The provider must never be allowed to authoritatively set:
- official `decision`,
- official `confidence`,
- `selected_concept_id`,
- trusted IDs,
- Agent MD levels,
- evidence confidence tiers,
- market numbers absent from the Evidence Graph.

The deterministic layer owns these fields.

The evaluator may propose qualitative judgments and critique text, but every object must pass contract validation before it can influence the decision engine.

## 8. Deterministic Hard Gates

PR D has a fail-closed gate stack.

### Gate 1 — Input Integrity

Pass only when:
- IDs are trusted and content-addressed where applicable,
- all candidate/evidence references resolve,
- `evolution_id` is consistent,
- PR C candidate admission is valid.

Integrity failure is a contract error, not an investment verdict. The engine stops rather than fabricating `HOLD`/`KILL`.

### Gate 2 — Evidence Coverage

Decision-critical claims for the baseline and any candidate considered for advancement must have normalized evidence.

A material unsupported claim becomes an explicit unknown and may trigger `HOLD`.

### Gate 3 — Counter-Evidence

A positive investment decision cannot be based only on supportive evidence.

`GO` or `MODIFY` requires material counter-evidence to be represented, or the completed research contract to record that the required counter-evidence search found no material contradiction.

### Gate 4 — Collision Completion

Material collision requests involving prior art, competitors, buyer evidence, regulation, technical dependency, or failure/blockers must be resolved before `GO` or `MODIFY`.

Unresolved material collision requests force `HOLD`.

### Gate 5 — Hard Blockers

Confirmed hard blockers can eliminate a baseline/candidate.

Examples:
- prohibited or unworkable regulation,
- technically infeasible dependency,
- clearly uneconomic buyer case,
- critical data unavailable under realistic constraints,
- unacceptable security/privacy requirement,
- distribution path that is structurally unavailable.

A blocker must be evidence-backed or explicitly deterministic; model assertion alone is insufficient.

### Gate 6 — Feasibility / Agent MD

Implementation feasibility is considered without turning automation level into a universal business-quality score.

Rules:
- Agent MD `T` feasibility is material to official advancement.
- `T3–T5` may advance if other gates pass.
- `T2` normally forces `HOLD` unless the feasibility artifact explicitly demonstrates that the blocking dependency has already been resolved.
- `T1` cannot produce `GO`/`MODIFY`; it results in `HOLD` when a plausible resolution path exists, otherwise the affected option is eliminated.
- Automation level `A` remains descriptive for general evaluations; `A4/A5` preference applies specifically to the Axion candidate/business strategy rather than every possible user idea.

### Gate 7 — Material Unknowns

Any unresolved unknown capable of reversing the decision blocks `GO`/`MODIFY`.

The engine surfaces the exact unknown and validation action rather than hiding it behind a confidence label.

### Gate 8 — Evolution Delta

`MODIFY` requires material improvement over the baseline, not different wording or extra features.

A candidate qualifies as materially improved only when:
- it passes all advancement gates,
- it changes at least one structural element such as buyer, problem framing, workflow position, value capture, or mechanism,
- normalized evaluation is strictly better than the baseline in at least two dimensions,
- at least one of those advantages is in `problem_evidence`, `buyer_economics`, `structural_differentiation`, or `technical_feasibility`,
- and it introduces no new unresolved hard blocker.

For comparison only, normalized dimension states have the ordered evidence interpretation `strong > mixed > weak`. `unknown` is never ranked; any decision-critical `unknown` triggers `HOLD` instead of participating in superiority math. No weighted total score is calculated.

## 9. Decision Algorithm

Decision order is deterministic and conservative.

### Step 1 — Validate inputs

If integrity contracts fail: raise a contract error and stop.

### Step 2 — Resolve research sufficiency

If material collision research or decision-critical evidence is unresolved: `HOLD`.

### Step 3 — Evaluate baseline and candidates

Classify each as:
- `eligible`
- `hold`
- `eliminated`

The classification is derived from hard gates, not provider preference.

### Step 4 — Determine `KILL`

Return `KILL` only when:
- the baseline is eliminated,
- every evolved candidate is eliminated,
- and the eliminations include evidence-backed decisive failure reasons.

If all options are merely uncertain rather than disproven, return `HOLD` instead.

### Step 5 — Determine `MODIFY`

First identify evolved candidates that satisfy the Evolution Delta gate against the baseline.

- If none qualify, continue to the `GO` test.
- If exactly one qualifies and all positive-decision gates pass, return `MODIFY` with that candidate.
- If more than one qualifies, one candidate may be selected only if it **strictly dominates every other qualifying candidate**: it must be better on at least one of the four anchor dimensions (`problem_evidence`, `buyer_economics`, `structural_differentiation`, `technical_feasibility`) and not worse on any of the ten dimensions, with no decision-critical unknowns.
- If no single candidate strictly dominates all other qualifying candidates, return `HOLD` and emit the smallest comparison experiment/research task that could distinguish them.

This rule deliberately prefers unresolved comparison over a fabricated ranking.

### Step 6 — Determine `GO`

Return `GO` when:
- the baseline is eligible,
- no evolved candidate qualifies for deterministic `MODIFY`,
- all positive-decision hard gates pass.

### Step 7 — Default safe outcome

Any unresolved decision-critical ambiguity maps to `HOLD`.

## 10. Confidence Contract

Official confidence is deterministic and separate from the verdict.

Allowed values remain `high`, `medium`, and `low`.

### `high`

Requires all of the following:
- no unresolved material unknowns,
- no unresolved material collision request,
- every material claim that directly supports the verdict has at least one current Tier A or Tier B evidence record,
- no unresolved Tier A/B contradiction capable of reversing the verdict,
- counter-evidence coverage is complete,
- no material evaluator-contract conflict remains.

### `medium`

Used when the verdict is stable but at least one non-critical or secondary aspect relies on Tier C, stale-but-still-relevant, or mixed evidence. No unresolved fact may be capable of reversing the verdict.

### `low`

Used when uncertainty is substantial and the safe verdict is `HOLD`, or when an evidence-backed `KILL` is directionally supported but some non-decision-critical details remain uncertain.

`GO`/`MODIFY` with `low` confidence is prohibited. A positive decision that would otherwise compute to low confidence becomes `HOLD`.

---

## 11. Tie and Disagreement Handling

PR D must not manufacture a winner when evidence cannot distinguish candidates.

If two or more candidates remain decision-admissible and no single candidate satisfies the strict-dominance rule:
- no candidate is selected,
- official decision becomes `HOLD`,
- the engine emits the smallest experiment or research task that would discriminate between them.

If evaluator qualitative recommendations conflict with deterministic gates, deterministic gates win and the disagreement is stored as an audit artifact.

---

## 12. State Update Rules

PR D produces a trusted decision result that a narrow state-update function applies.

### For `GO`
- `decision = "GO"`
- `selected_concept_id = null`
- `evolved_idea` remains null unless a prior non-decision workflow explicitly populated it; the handoff still uses the original idea
- confidence is set by the deterministic confidence contract

### For `MODIFY`
- `decision = "MODIFY"`
- `selected_concept_id = <trusted candidate_id>`
- `evolved_idea = selected_candidate["one_sentence_concept"]`
- confidence is set by the deterministic confidence contract

### For `HOLD`
- `decision = "HOLD"`
- downstream spec/package generation remains blocked
- unresolved material questions and next validation must be present

### For `KILL`
- `decision = "KILL"`
- downstream spec/package generation remains blocked
- evidence-backed kill reasons must be present

Human approval remains a separate boundary. PR D never sets `human_decision = proceed` on behalf of the user.

## 13. Proposed Modules

Expected PR D code boundaries:

```text
src/idea_vending/
  evaluator_contract.py
  baseline_contract.py
  independent_evaluator.py
  decision_engine.py

tests/
  test_evaluator_contract.py
  test_baseline_contract.py
  test_independent_evaluator.py
  test_decision_engine.py
```

### `baseline_contract.py`
Creates and validates the content-addressed raw-idea comparison baseline.

### `evaluator_contract.py`
Defines provider-neutral request/response schemas, dimension vocabulary, critique records, and evidence-reference validation.

### `independent_evaluator.py`
Builds evaluator requests and ingests provider output as untrusted data. It has no official decision authority.

### `decision_engine.py`
Runs deterministic hard gates, baseline-vs-candidate comparison, strict-dominance handling, official verdict derivation, confidence derivation, and safe state-update result creation.

## 14. Failure Modes

PR D must fail closed for:
- malformed evaluator output,
- unknown candidate IDs,
- candidate content/ID mismatch,
- unknown claim IDs,
- mismatched evolution IDs,
- missing candidate admission audit,
- provider attempts to set trusted decision fields,
- incomplete counter-evidence,
- unresolved material collision requests,
- unsupported hard blockers,
- unknown Agent MD feasibility vocabulary,
- multiple qualifying candidates without strict dominance,
- positive decision with low confidence,
- `MODIFY` without a trusted selected candidate,
- `KILL` caused solely by missing evidence.

Errors in data integrity must not be silently converted into business judgments.

---

## 15. Security and Prompt-Injection Boundary

Research text and evaluator output are data, not instructions.

Requirements:
- raw research remains untrusted,
- evaluator/provider text cannot alter system policy or trusted IDs,
- no raw HTML/model output is rendered unsafely,
- no API keys or provider credentials enter the public repository,
- official decisions must be reconstructable from stored structured artifacts,
- deterministic validation runs after every probabilistic output boundary.

## 16. TDD / Acceptance Matrix

PR D implementation must introduce tests RED-first for at least the following cases:

1. valid baseline receives deterministic content-addressed ID.
2. tampered baseline ID is rejected.
3. evaluator cannot supply official decision/confidence/selected concept.
4. evaluator cannot reference unknown candidate or claim IDs.
5. all ten evaluation dimensions are required exactly once.
6. unsupported factual rationale is rejected or represented as explicit unknown.
7. positive decision with no counter-evidence coverage is blocked.
8. unresolved material collision request forces `HOLD`.
9. material unknown capable of reversing the decision forces `HOLD`.
10. confirmed hard blocker eliminates the affected option.
11. unresolved `T2` feasibility forces `HOLD`.
12. `T1` cannot produce `GO` or `MODIFY`.
13. missing evidence alone never produces `KILL`.
14. baseline eligible plus no materially superior candidate produces `GO`.
15. exactly one materially superior eligible evolved candidate produces `MODIFY`.
16. multiple qualifying candidates without one strict dominator produce `HOLD`.
17. one qualifying candidate that strictly dominates all other qualifying candidates may produce `MODIFY`.
18. `MODIFY` sets trusted `selected_concept_id` and string `evolved_idea` from `one_sentence_concept`.
19. baseline and all candidates decisively eliminated produce `KILL`.
20. `GO`/`MODIFY` with computed low confidence is prohibited.
21. decision engine never mutates `human_decision`.
22. existing v0.2, PR A, PR B, and PR C tests remain green.
23. final Production Gate ends with `GREEN WITH EVIDENCE`.

## 18. Completion Criteria

PR D is complete only when:
- generation and evaluation responsibilities remain separated,
- the raw idea has a stable comparison baseline,
- no provider output can directly set trusted decision state,
- every official positive decision is traceable to evidence and counter-evidence,
- missing evidence safely becomes `HOLD`, not false `GO` or false `KILL`,
- `MODIFY` requires demonstrable structural Evolution Delta,
- indistinguishable finalists do not create a fake winner,
- `KILL` requires affirmative failure evidence,
- official confidence is deterministic,
- the existing string type of `Evolution State.evolved_idea` is preserved,
- human approval remains separate,
- all prior regression tests pass,
- exact-head Production Gate returns `GREEN WITH EVIDENCE`.

Only after PR D is merged should PR E connect the full evolution pipeline to the executive-first UX and end-to-end benchmark gate.
