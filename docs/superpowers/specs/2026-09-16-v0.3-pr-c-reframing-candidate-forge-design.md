# Idea Vending Machine v0.3 — PR C Reframing + Candidate Forge Design

## 1. Purpose

PR C implements the first genuinely creative intelligence layer of Idea Vending Machine v0.3.

PR A established the executive decision contract. PR B established the evidence/research contract. PR C must now transform a researched raw idea into materially different, higher-value candidate concepts without allowing free-form model output to bypass evidence, structural constraints, or later independent evaluation.

The objective is not to make the user's idea sound smarter. The objective is to discover what the idea should become.

Core rule:

> Creative generation may be probabilistic; admission into the candidate set is deterministic and evidence-traceable.

PR C therefore separates:

1. **Problem reframing** — identify deeper problem structures and obsolete assumptions.
2. **Transformation testing** — systematically test multiple perspective changes.
3. **Cross-industry mechanism transfer** — import reusable causal mechanisms, not cosmetic features.
4. **Candidate forge** — generate materially different concept families.
5. **Deterministic candidate validation** — reject candidates that cannot explain causal value creation, evidence links, or meaningful difference from the raw idea.

PR C does **not** decide which candidate wins. Independent critique and final GO/MODIFY/HOLD/KILL judgment remain PR D responsibilities.

---

## 2. Position in the v0.3 pipeline

```text
RAW IDEA
  ↓
PR A — EVOLUTION STATE / EXECUTIVE CONTRACT
  ↓
PR B — LANDSCAPE RESEARCH / EVIDENCE GRAPH
  ↓
PR C — ASSUMPTION MAP
  ↓
PR C — REFRAME / TRANSFORMATION TESTS
  ↓
PR C — CROSS-INDUSTRY MECHANISM TRANSFER
  ↓
PR C — CANDIDATE FORGE
  ↓
PR B — COLLISION RESEARCH
  ↓
PR D — INDEPENDENT CRITIQUE / DECISION
```

PR C consumes validated research artifacts and produces structured candidate artifacts. It must not overwrite the original idea or invent unsupported factual claims.

## 3. Architectural approach

### Chosen approach — Hybrid Expert Forge

PR C uses a hybrid architecture:

- **Probabilistic ideation provider** for broad associative reasoning, unconventional reframing, and cross-domain synthesis.
- **Deterministic orchestration and validation** for vocabulary, object shape, evidence links, diversity requirements, causal chains, and rejection rules.

This approach is chosen over two alternatives:

### Alternative A — Fully deterministic transformation engine

Advantages:
- highly reproducible
- easy to test
- low runtime uncertainty

Disadvantages:
- insufficient novelty
- tends to create formulaic outputs
- weak at distant analogy and mechanism discovery

Rejected because the product's differentiating value depends on high-quality conceptual synthesis.

### Alternative B — Free-form LLM innovation agent

Advantages:
- highly flexible
- potentially creative
- low implementation friction

Disadvantages:
- inconsistent output
- novelty theater
- persuasive but unsupported claims
- weak reproducibility
- candidate collapse into minor feature variations
- difficult to verify

Rejected because it violates `NO GREEN WITHOUT EVIDENCE`.

### Hybrid Expert Forge responsibilities

```text
Validated Evidence Graph
        ↓
Deterministic Context Builder
        ↓
Ideation Provider
        ↓
Structured Reframe / Mechanism / Candidate Objects
        ↓
Deterministic Validators
        ↓
Validated Candidate Set
```

No provider response enters the official state until it passes deterministic validation.

## 4. Data contracts

PR C introduces three primary artifact classes.

### 4.1 Assumption Map

The Assumption Map records assumptions embedded in the raw idea and current workflow.

Required fields:

```text
assumption_id
statement
assumption_type
scope
why_it_exists
supporting_claim_ids
contradicting_claim_ids
status
```

Allowed `assumption_type` values:

- `workflow`
- `customer_behavior`
- `business_model`
- `technology`
- `regulation`
- `distribution`
- `data`
- `economics`

Allowed `status` values:

- `supported`
- `weak`
- `contested`
- `unsupported`
- `unknown`

Rules:
- Every assumption must preserve a plain-language statement.
- Material external assertions require Evidence Graph claim IDs.
- `unknown` is valid and preferred over invented certainty.
- Assumptions are hypotheses about the current model, not conclusions about the final candidate.

---

### 4.2 Mechanism Transfer

A cross-industry transfer represents a reusable causal mechanism, not a brand or feature list.

Required fields:

```text
transfer_id
source_domain
mechanism_name
mechanism_description
source_constraint
why_it_works_there
target_equivalent_constraint
transfer_logic
value_chain_change
expected_customer_value
new_risks
supporting_claim_ids
```

A valid transfer must explain the causal sequence:

```text
Source industry has constraint X
        ↓
Mechanism M changes behavior/process Y
        ↓
Target problem contains equivalent constraint X'
        ↓
Applying M changes target process Y'
        ↓
Customer receives measurable or clearly stated value Z
```

Invalid examples:
- "Use Stripe-style UX"
- "Add an Uber-like marketplace"
- "Combine blockchain + AI + analytics"

Valid examples must explain **what mechanism is transferred and why the economics or behavior changes**.

---

### 4.3 Candidate Concept

Each candidate is a structured proposal, not free-form marketing copy.

Required fields:

```text
candidate_id
family
name
one_sentence_concept
problem_reframe
primary_buyer
user
job_to_be_done
assumptions_broken
transformations_used
mechanism_transfer_ids
workflow_before
workflow_after
value_creation_chain
value_capture_model
automation_thesis
defensibility_thesis
compounding_effect
critical_dependencies
new_risks
evidence_claim_ids
unknowns
validation_questions
```

Allowed `family` values:

- `adjacent_innovation`
- `category_shift`
- `zero_based_reinvention`
- `axion_candidate`

Candidate IDs must be unique within an evolution.

## 5. Reframing Engine

The Reframing Engine must not jump from research directly to candidate generation.

It first creates a structured map of the current problem:

```text
Visible symptom
  ↓
User pain
  ↓
Economic loss / risk
  ↓
Root constraint
  ↓
Current workaround
  ↓
Embedded assumptions
```

The engine then applies transformation operators.

### Canonical transformation vocabulary

- `AFTER_TO_BEFORE`
- `REPAIR_TO_PREVENT`
- `SEARCH_TO_PREDICT`
- `ADVISE_TO_EXECUTE`
- `INPUT_TO_OBSERVE`
- `TOOL_TO_WORKFLOW`
- `WORKFLOW_TO_INFRASTRUCTURE`
- `DOCUMENT_TO_DATA`
- `DATA_TO_DECISION`
- `DECISION_TO_ACTION`
- `SERVICE_TO_ASSET`
- `ONE_TIME_TO_COMPOUNDING`

The engine is not required to apply every transformation. It must record:

```text
transformation
applicable: true/false
reason
resulting_reframe
materiality
```

Allowed materiality:
- `none`
- `minor`
- `material`

At least two materially different transformations must be tested before a candidate set may be marked generation-ready, unless the system explicitly records that the original idea is already structurally strong and further transformation is low-value.

---

## 6. Assumption Destruction rules

PR C must actively challenge, not merely list, assumptions.

Each assumption challenge records:

```text
assumption_id
challenge_question
remove_or_invert_test
expected_effect_if_false
new_opportunity_if_false
new_risk_if_false
```

Examples of challenge questions:

- Does a human actually need to initiate this process?
- Does this event need to be handled after it occurs?
- Does the document need to remain the unit of work?
- Does the buyer need another tool, or do they need the task to disappear?
- Could the system observe the signal automatically instead of requesting input?
- Could a one-time deliverable become reusable infrastructure or a compounding asset?

The system must be allowed to conclude that an assumption should **not** be destroyed. Forced novelty is a failure mode.

## 7. Cross-Industry Mechanism Discovery

The mechanism-transfer step uses evidence and analogy, but must avoid copying superficial product patterns.

### Search objective

Instead of searching only for direct competitors, the system should identify domains with structurally similar constraints such as:

- information asymmetry
- trust verification
- matching
- risk pricing
- provenance
- transaction abstraction
- coordination overhead
- queue/latency reduction
- prediction under uncertainty
- fraud prevention
- compliance automation
- compounding data advantage

### Required transfer test

A mechanism may enter the candidate context only if all six questions can be answered:

1. What exact mechanism is being transferred?
2. Why does it work in the source domain?
3. What equivalent constraint exists in the target domain?
4. What step or incentive changes in the target value chain?
5. What new customer value is created?
6. What new risk or dependency is introduced?

A transfer missing any one of these is invalid.

## 8. Candidate Forge

The Candidate Forge must generate **at least four candidate families**, one per canonical family, unless a family is explicitly marked non-applicable with reason.

### 8.1 Adjacent Innovation

Purpose:
- preserve the basic category
- remove obvious friction
- improve value dramatically without category change

This candidate provides a conservative reference point.

### 8.2 Category Shift

Purpose:
- redefine what category actually solves the problem
- move from feature/tool to workflow, platform, infrastructure, risk engine, marketplace, standard, or another structurally different form when justified

A valid Category Shift must alter at least two of:
- buyer
- workflow position
- unit of value
- business model
- responsibility boundary

### 8.3 Zero-Based Reinvention

Question:

> If today's AI, automation, APIs, data availability, and computing existed when this industry workflow was first designed, how would we design the workflow from zero?

The result must not preserve legacy steps without justification.

### 8.4 Axion Candidate

Optimizes for the user's established operating constraints:

- A4/A5 automation preference
- capital efficiency
- repeatability
- delivery reliability
- high gross-margin potential
- minimal fixed-time human labor
- verifiable outputs
- no SaaS-first assumption

This candidate may still be rejected later by PR D if evidence, feasibility, or economics are weak.

## 9. Candidate diversity contract

Candidate Forge fails if all candidates are cosmetic variants.

A deterministic diversity audit compares:

- primary buyer
- problem reframe
- workflow after
- value creation chain
- value capture model
- transformations used
- mechanism transfers

Minimum rule:
- Each candidate must differ materially from at least two other candidates on at least **three** structural dimensions.
- A candidate whose only differences are features, branding, or interface details is invalid.

The audit returns:

```text
diversity_ready: true/false
pairwise_differences
collapsed_candidate_ids
```

Collapsed candidates are rejected or regenerated.

---

## 10. Causal Value Chain contract

Every candidate must explain why it creates new value.

Canonical form:

```text
Current constraint
  ↓
Intervention / transferred mechanism
  ↓
Workflow or incentive change
  ↓
Operational or economic effect
  ↓
Buyer value
  ↓
Value capture
```

Candidate validation fails if the chain contains unsupported leaps such as:

- "AI improves efficiency" without identifying the work eliminated or changed.
- "Marketplace creates network effects" without identifying both sides and reinforcing behavior.
- "Data creates a moat" without explaining acquisition, accumulation, and switching advantage.
- "Automation saves money" without identifying the human step or error/risk cost displaced.

This gate is the main defense against novelty theater.

## 11. Evidence discipline

PR C may create hypotheses, but it must label them as hypotheses.

### Factual claim rules

- Material external factual claims must reference existing Evidence Graph `claim_id`s.
- New factual claims discovered during candidate generation cannot silently become facts; they become research requests for Collision Research.
- Hypotheses are stored separately from evidence-backed statements.
- Candidate confidence is **not** decided in PR C.

### Research requests emitted by PR C

Each candidate may produce:

```text
research_request_id
candidate_id
question
reason
materiality
suggested_category
```

Allowed suggested categories include:
- `prior_art`
- `competitors`
- `buyer_evidence`
- `pricing`
- `regulation`
- `technical_dependency`
- `failure_or_blockers`

These feed PR B's Collision Research path.

## 12. IdeationProvider boundary

PR C must not hard-code one model vendor.

Provider-facing request shape:

```text
operation
objective
raw_idea
problem_context
assumption_context
evidence_summary
allowed_transformations
required_output_schema
constraints
```

Supported operation vocabulary for PR C:

- `extract_assumptions`
- `challenge_assumptions`
- `propose_reframes`
- `discover_mechanisms`
- `forge_candidates`

Provider output is treated as untrusted structured data until validated.

No provider may:
- write directly to repository files
- execute code
- mutate Evolution State directly
- mark a candidate approved
- set GO/MODIFY/HOLD/KILL

---

## 13. Deterministic validation gates

A Candidate Set is `forge_ready=true` only when all gates pass.

### Gate A — Schema
- exact required fields
- closed vocabularies respected
- non-empty critical fields
- unique IDs

### Gate B — Evidence traceability
- referenced claim IDs exist in Evidence Graph
- unsupported facts are not marked as evidence-backed

### Gate C — Reframe materiality
- candidate explains what materially changed from raw idea

### Gate D — Mechanism integrity
- mechanism transfers explain causal logic, not brand analogy

### Gate E — Causal value chain
- no missing link between intervention and buyer value

### Gate F — Candidate diversity
- candidate set does not collapse into feature variations

### Gate G — Unknowns / research requests
- material unknowns are explicit
- unsupported decision-critical questions emit Collision Research requests

No candidate gets a "best" label in PR C.

---

## 14. Error handling and recovery

### Provider failure

If the ideation provider times out, returns malformed output, or violates the schema:
- retain the last valid artifacts
- record provider failure metadata
- do not mutate validated candidate state
- allow retry with the same provider or another adapter

### Validation failure

Validation errors are categorized:
- `schema_failure`
- `evidence_failure`
- `causal_chain_failure`
- `mechanism_failure`
- `diversity_failure`
- `unsupported_claim_failure`

The orchestration layer may request targeted regeneration of only the failed artifact instead of regenerating the entire assessment.

### No meaningful reframe found

This is a valid result.

The system records:

```text
reframe_outcome: original_remains_strong
```

It must not force a worse idea merely to appear innovative.

---

## 15. Security and trust boundaries

PR C inherits PR B's rule that external text is untrusted data.

Additional rules:

1. Provider prompts contain only the minimum evidence summaries necessary for the operation.
2. Raw web content is never inserted into system-level instructions.
3. Provider output cannot contain executable repository actions.
4. Candidate text is rendered as data, not HTML.
5. URLs, scripts, or code snippets inside provider output do not execute automatically.
6. No secrets are sent to ideation providers through the PR C contract.
7. Candidate IDs and evidence IDs are generated/validated by deterministic code, not blindly trusted from model output.

## 16. Test strategy

PR C uses TDD and expands the existing Production Gate.

### Unit tests — Assumption Map

Must cover:
- stable schema
- closed vocabularies
- unknown status allowed
- invalid evidence refs rejected
- original statements preserved

### Unit tests — Transformations

Must cover:
- exact transformation vocabulary
- applicable/non-applicable records
- materiality vocabulary
- generation-ready requirement for materially distinct tests
- valid "original remains strong" outcome

### Unit tests — Mechanism Transfer

Must reject:
- brand-only analogies
- missing target constraint
- missing value-chain change
- missing new-risk field
- unknown supporting claim IDs

### Unit tests — Candidate Concept

Must cover:
- exact family vocabulary
- required fields
- unique candidate IDs
- evidence ref integrity
- hypotheses/unknowns preserved
- no winner/score field allowed

### Unit tests — Diversity Audit

Must detect:
- four names describing the same idea
- feature-only differences
- structurally distinct buyer/workflow/business-model candidates

### Unit tests — Causal Chain

Must reject candidates with missing:
- current constraint
- mechanism/intervention
- workflow effect
- buyer value
- value capture

### Integration tests

A representative fixture must demonstrate:

```text
Evidence Graph
→ Assumption Map
→ Reframes
→ Mechanism Transfers
→ Four Candidate Families
→ Diversity Audit
→ Collision Research Requests
```

without network access.

### Regression tests

All existing v0.1, v0.2, PR A, and PR B tests must continue passing.

## 17. PR C acceptance criteria

PR C is complete only when:

1. Assumption Map contract exists and is validated.
2. Canonical transformation vocabulary is implemented.
3. Assumption challenge artifacts are supported.
4. Cross-industry Mechanism Transfer contract exists and rejects superficial analogy.
5. Candidate Concept contract supports all four canonical families.
6. Candidate diversity audit detects collapsed variants.
7. Causal Value Chain validation blocks novelty theater.
8. Evidence references are checked against PR B Evidence Graph.
9. Unsupported material claims become hypotheses or Collision Research requests.
10. No candidate may self-declare itself the winner.
11. No final GO/MODIFY/HOLD/KILL decision is made in PR C.
12. Existing v0.2 and v0.3 behavior remains unchanged.
13. `python scripts/verify.py` passes.
14. GitHub Actions Production Gate finishes with `GREEN WITH EVIDENCE`.

---

## 18. Explicitly out of scope

PR C does not include:

- Independent Investment Judge
- final candidate ranking or selection
- GO/MODIFY/HOLD/KILL decision logic
- Executive UX
- live production search-provider credentials
- persistent database
- autonomous code generation
- automatic deployment
- billing/auth/SaaS operations

Those remain PR D/PR E or later work.

## 19. Planned implementation units

After this design is approved, implementation should be split into small TDD tasks:

1. `idea_evolution.py` — Assumption Map + transformation records.
2. `mechanism_transfer.py` — cross-industry mechanism contract and validation.
3. `candidate_forge.py` — Candidate Concept schema and candidate set validation.
4. `candidate_diversity.py` — structural diversity audit.
5. `collision_requests.py` — unresolved candidate hypotheses → PR B research requests.
6. Integration tests and README update.

The exact filenames may be adjusted in the implementation plan if existing module boundaries suggest a cleaner decomposition, but responsibilities must remain separated.

## 20. Definition of success

PR C succeeds when the system can take a researched raw idea and produce a set of **structurally different, evidence-aware, causally explained candidate concepts** that are ready to be attacked by PR D's independent evaluator.

A visually impressive candidate list is not success.

Success means:

- the original idea has been challenged,
- assumptions are explicit,
- transformations were tested,
- borrowed mechanisms have causal justification,
- candidates differ in business architecture rather than wording,
- material claims are traceable or marked unproven,
- and no candidate bypasses later independent judgment.

`NO GREEN WITHOUT EVIDENCE` remains mandatory.
