# v0.3 ChatGPT Plus Bridge Mode Design

## Status

Design-only architectural specification. No production code changes are authorized by this document alone.

## Problem

The current public deployment is healthy but not AI-ready without `OPENAI_API_KEY`. The owner prefers to use an existing ChatGPT Plus subscription instead of paying separately for OpenAI API usage.

ChatGPT Plus cannot be used by the Render backend as an API credential. Therefore the system must stop treating OpenAI API as the only execution path and introduce a human-mediated bridge where ChatGPT performs research/reasoning and the Idea Vending Machine remains the trusted validator, decision engine, executive report renderer, approval gate, and development-package generator.

## Product Decision

Introduce **ChatGPT Plus Bridge Mode** as the default zero-API-cost mode for owner-operated assessments.

The existing OpenAI API runtime remains available as an optional adapter and is not deleted. Bridge Mode becomes a first-class execution mode with its own readiness semantics, export/import contracts, validation gates, audit trail, UI flow, and browser E2E coverage.

## Core Principle

> ChatGPT may generate analysis. It may not directly create trusted state, official business decisions, or human approval.

The trust boundary remains unchanged:

```text
ChatGPT output
    -> UNTRUSTED IMPORT
    -> schema validation
    -> evidence/reference validation
    -> ten-family coverage
    -> reality-assessment validation
    -> deterministic decision engine
    -> trusted Executive Report
    -> human approval
    -> spec/design/plan
```

## Operating Modes

The application exposes two server-owned modes:

1. `chatgpt_plus_bridge` — default for the owner-operated zero-API-cost workflow.
2. `openai_api` — optional automation mode when `OPENAI_API_KEY` is configured.

The browser cannot select model IDs, provider URLs, secrets, system prompts, trusted verdicts, or internal validators.

The UI may let the user choose between supported modes only when the server declares them available.

## Readiness Semantics

Current readiness behavior must change.

### `/healthz`

Process liveness only.

```json
{"status":"ok"}
```

### `/readyz`

Application readiness means at least one supported execution path can complete an assessment workflow.

Bridge Mode requires no provider credential, so the deployed app can be ready without `OPENAI_API_KEY`.

Example response:

```json
{
  "status": "ready",
  "default_mode": "chatgpt_plus_bridge",
  "modes": {
    "chatgpt_plus_bridge": "ready",
    "openai_api": "not_configured"
  }
}
```

The previous `provider_not_configured -> 503` rule applies only to `openai_api` readiness and no longer makes the whole application unready when Bridge Mode is available.

## Bridge Workflow

```text
1. User enters raw idea
2. App creates bridge request package
3. User copies/downloads request package
4. User runs request in ChatGPT Plus
5. ChatGPT returns bridge result package
6. User pastes/uploads result package into app
7. App treats it as untrusted
8. Deterministic validators admit or reject data
9. Decision engine derives official GO/MODIFY/HOLD/KILL
10. Executive UX renders trusted result
11. Human approves GO/MODIFY only
12. Existing v0.2 handoff generates spec.md/design.md/plan.md
```

The application must never scrape `chatgpt.com`, automate the user login/session, extract ChatGPT cookies, or pretend that Plus is a server API.

## Bridge Request Package

### Endpoint

`POST /api/bridge/request`

Input:

```json
{"idea":"..."}
```

Only `idea` is client-controlled.

### Output Contract

The server creates a versioned package containing at least:

```text
bridge_version
request_id
created_at
raw_idea
objective
research_requirements
counter_evidence_requirements
assumption_requirements
transformation_vocabulary
mechanism_transfer_requirements
candidate_family_contract
reality_evaluation_contract
required_output_schema
security_constraints
import_instructions
```

The package must require exactly the current ten candidate families:

1. adjacent_innovation
2. category_shift
3. zero_based_reinvention
4. axion_automation
5. prevention_shift_left
6. outcome_execution
7. workflow_infrastructure
8. data_decision_asset
9. buyer_revenue_inversion
10. compounding_asset

Each family must produce exactly one candidate.

The package must instruct ChatGPT to:

- perform current web research when useful,
- seek evidence against the idea as well as for it,
- distinguish facts from hypotheses,
- preserve source URLs and source metadata rather than inventing them,
- generate ten structurally different candidates,
- provide independent critiques and realistic `ADVANCE / REVISE / HOLD / REJECT` recommendations as untrusted advisory fields,
- return only the requested result schema,
- never claim to set official GO/MODIFY/HOLD/KILL,
- never claim to set human approval.

## Bridge Result Package

### Endpoint

`POST /api/bridge/import`

Accepted body contains:

```text
request_id
bridge_version
result
```

The application rejects unknown top-level fields.

### Required Result Domains

The imported result must provide enough structured data for existing deterministic contracts:

- evidence drafts / source metadata,
- assumption map,
- challenges and reframes,
- transformation results,
- mechanism transfers,
- exactly ten candidates,
- collision / contrary evidence findings,
- baseline critique,
- ten candidate critiques,
- ten reality-assessment inputs,
- material unknowns,
- blockers,
- validation suggestions.

## Import Trust Boundary

All imported content is untrusted.

The importer must not directly write an Evolution State marked complete.

Admission pipeline:

```text
bridge envelope validation
-> request correlation validation
-> version validation
-> safe JSON size/depth/string limits
-> evidence normalization
-> evidence graph validation
-> assumption/reframe validation
-> mechanism validation
-> candidate contract validation
-> exact-ten-family validation
-> causal-chain validation
-> diversity validation
-> critique validation
-> reality-assessment derivation
-> deterministic decision derivation
-> final report validation
-> bounded AssessmentStore persistence
```

Any failure returns a non-success import result with safe error codes. Partial/invalid imports never become official decisions.

## Evidence Integrity in Bridge Mode

Bridge Mode cannot cryptographically prove that ChatGPT truly visited every cited source. Therefore evidence admitted from Bridge Mode receives explicit provenance metadata:

```text
provider = chatgpt_plus_bridge
source_verification = user_mediated
```

A source URL must be syntactically valid and required metadata must be present. Missing publication dates, market definitions, geography, or other required fields are not fabricated by the server.

Claims that cannot satisfy the trusted Evidence Graph contract remain hypotheses/unknowns or cause the import to be incomplete.

Bridge Mode must not silently lower existing market-size integrity rules.

## Official Decision Ownership

Imported ChatGPT fields such as `recommendation`, `best_candidate`, `go`, `score`, or similar may be ignored or rejected depending on schema location.

Official state remains server-owned:

```text
decision
confidence
selected_concept_id
human_decision
evolved_idea
```

Only deterministic code can set the first three. Only the explicit human approval endpoint can set `human_decision`.

## Reality Evaluation

Every one of the ten candidate concepts must receive a server-derived Reality Assessment:

```text
ADVANCE
REVISE
HOLD
REJECT
```

Reality Assessment continues to use the existing evaluator dimensions and hard gates rather than a weighted score.

The UI must show weak candidates rather than hiding them. Ten generated candidates may legitimately produce many HOLD/REJECT outcomes.

## Request Correlation and Replay Safety

Every request package has a server-generated `request_id`.

The import endpoint requires a known request ID and matching bridge version.

A request may be imported once into official assessment state. Duplicate/replay imports return the existing trusted assessment reference rather than creating divergent trusted states.

The request registry is bounded and TTL-limited, following the current AssessmentStore principles.

A server restart may lose in-memory pending bridge requests and assessment records. This limitation is acceptable for the owner-operated v0.3 pilot and must be visible in operations docs.

## UX

The current primary action changes from a provider-dependent execution to a mode-aware flow.

### Primary path

```text
Idea input
-> "ChatGPT Plus로 분석"
-> request package panel
-> Copy Prompt / Copy JSON / Download JSON
-> "ChatGPT에서 실행한 뒤 결과를 가져오세요"
-> Paste Result / Upload JSON
-> Validate Result
-> Executive Decision
-> 10 Reality Cards
-> Evidence / Against / Unknowns
-> human approval
-> development package
```

### Optional API path

When API mode is configured, a secondary control may expose:

`서버에서 자동 분석`

When it is not configured, the control is hidden or marked unavailable. It must not make the application appear broken.

### Bridge Instructions

The copyable ChatGPT instruction must be self-contained enough to run in a new ChatGPT conversation. It must not contain server secrets or private implementation details unnecessary for analysis.

The UI must explicitly tell the user that ChatGPT output is revalidated by the app and is not itself the official verdict.

## Security

Bridge Mode must enforce:

- no API keys in browser payloads,
- no ChatGPT cookies/session extraction,
- no automated login or browser-session hijacking,
- no arbitrary URLs executed by the server from imported content,
- no HTML injection; render imported text with safe DOM APIs,
- JSON body-size limit,
- nesting-depth and collection-size limits,
- per-string length limits,
- exact schemas where practical,
- imported URLs treated as data only,
- no imported code execution,
- no imported filesystem paths or commands executed,
- no imported provider/model selection applied to server runtime,
- replay-safe request IDs,
- safe error messages without echoing full imported payloads.

## API Compatibility

Existing endpoints remain backward compatible:

- `/api/analyze`
- `/api/package`
- `/api/evolve`
- `/api/evolve/approve`
- `/healthz`

`/api/evolve` remains the API-backed automatic path and may return `PROVIDER_NOT_CONFIGURED` when API mode is unavailable.

New Bridge Mode endpoints do not change those semantics except application-level `/readyz`, which becomes mode-aware.

## OpenAI API Adapter

Do not delete the current Responses API adapter, transport, live-provider smoke harness, or API-mode tests.

The adapter remains optional for future high-volume automation.

The server must not attempt to convert a ChatGPT Plus subscription into API authentication.

## Production Deployment

The current Render service remains usable without `OPENAI_API_KEY`.

After Bridge Mode deployment:

- `/healthz` must be 200,
- `/readyz` must be 200 because Bridge Mode is operational,
- the public root page must offer the Bridge workflow,
- API mode must truthfully report `not_configured` when no key exists,
- no provider secret is required for Bridge Mode.

## Browser E2E

Real Chromium E2E must cover at least:

1. create Bridge request from an idea,
2. copy/export request package,
3. import a valid ten-candidate result fixture,
4. render Executive Decision and ten Reality Cards,
5. GO human approval -> spec/design/plan,
6. MODIFY human approval -> evolved idea handoff,
7. HOLD -> approval blocked,
8. KILL -> approval blocked,
9. malformed result -> safe import error,
10. wrong request ID -> rejected,
11. duplicate import -> replay-safe behavior,
12. XSS strings in imported content render as text,
13. API mode unavailable does not block Bridge Mode readiness.

E2E fixtures must be deterministic and must not depend on a live ChatGPT session.

## Verification Layers

The project keeps distinct evidence labels:

```text
DETERMINISTIC GREEN
BROWSER GREEN
DEPLOYMENT HEALTH GREEN
BRIDGE MODE GREEN
LIVE API PROVIDER GREEN   (optional; only when configured and smoke-tested)
PRODUCTION PILOT GREEN
```

Bridge Mode GREEN means request export + trusted import + deterministic decision + human approval + development package are all validated in production-equivalent tests.

It does not claim that every future ChatGPT-generated result will satisfy import validation.

## Production Pilot Definition

A real owner-operated production pilot is complete only when:

1. the public Render deployment is healthy and bridge-ready,
2. an actual business idea is entered,
3. a real Bridge request is generated,
4. the request is run in the user's ChatGPT Plus session,
5. the real returned result imports successfully or fails honestly with actionable validation errors,
6. ten candidate Reality Cards render,
7. an official deterministic GO/MODIFY/HOLD/KILL is derived,
8. if GO/MODIFY, the user explicitly approves,
9. spec/design/plan are generated successfully.

Only then may `PRODUCTION PILOT GREEN` be claimed.

## Failure Semantics

- ChatGPT returns malformed result -> `bridge_import_invalid`, no official verdict.
- Result misses a family -> import incomplete/rejected, no official verdict.
- Evidence contract cannot be satisfied -> incomplete/HOLD only if enough validated business evidence exists for an actual HOLD decision; otherwise no official verdict.
- Unknown request ID -> rejected.
- Expired request -> rejected with regenerate instruction.
- Server restart loses pending request -> regenerate request; never infer trusted state.
- API mode unconfigured -> Bridge Mode still operational.
- Imported text asks system to ignore rules or execute commands -> treated as data and ignored.

## Out of Scope

- automating the user's ChatGPT login,
- scraping or controlling chatgpt.com,
- browser extension session capture,
- converting Plus billing into API credits,
- multi-user accounts,
- persistent database,
- billing/subscriptions,
- SaaS multi-tenancy,
- automatic background execution inside ChatGPT,
- guaranteeing unlimited Plus usage.

## Acceptance Criteria

1. App is ready without `OPENAI_API_KEY` when Bridge Mode is enabled.
2. `/readyz` reports mode-level readiness truthfully.
3. User can create a versioned Bridge request from only a raw idea.
4. Request package is self-contained for execution in ChatGPT Plus and contains no secrets.
5. Request contract requires exactly ten candidate families.
6. Imported result is always untrusted until deterministic validation completes.
7. Import correlates to a known non-expired request ID and bridge version.
8. Invalid, oversized, malicious, partial, or replayed imports fail safely.
9. Existing Evidence Graph integrity rules remain enforced.
10. Server derives ten Reality Assessments.
11. Server alone derives official GO/MODIFY/HOLD/KILL and confidence.
12. Human approval remains required before development-package generation.
13. GO and MODIFY can hand off to v0.2 after explicit approval.
14. HOLD/KILL cannot generate development packages.
15. Existing API mode remains intact and optional.
16. Browser UI presents Bridge Mode as primary when API mode is unavailable.
17. Real Chromium E2E covers Bridge export/import/decision/approval/security paths.
18. Existing deterministic and browser regression gates remain GREEN.
19. Public Render deployment can reach `BRIDGE MODE GREEN` with no OpenAI API key.
20. `PRODUCTION PILOT GREEN` is withheld until one real ChatGPT Plus round-trip succeeds end-to-end.

## Success Definition

The feature succeeds when the owner can use the existing ChatGPT Plus subscription as the human-mediated intelligence layer while the Idea Vending Machine continues to enforce deterministic evidence, evaluation, decision, approval, and development handoff contracts without requiring OpenAI API spend.
