# v0.3 ChatGPT Plus Bridge Mode Design

## Status

Design-only architectural specification. No production code changes are authorized by this document alone.

## Problem

The current public deployment is healthy but not AI-ready without `OPENAI_API_KEY`. The owner prefers to use an existing ChatGPT Plus subscription instead of paying separately for OpenAI API usage.

ChatGPT Plus cannot be used by the Render backend as an API credential. Therefore the system must stop treating OpenAI API as the only execution path and introduce a human-mediated bridge where ChatGPT performs research/reasoning and the Idea Vending Machine remains the trusted validator, decision engine, executive report renderer, approval gate, and development-package generator.

## Product Decision

Introduce **ChatGPT Plus Bridge Mode** as the default zero-API-cost mode for owner-operated assessments.

The existing OpenAI API runtime remains available as an optional adapter and is not deleted. Bridge Mode becomes a first-class execution mode with its own readiness semantics, export/import contracts, validation gates, audit trail, UI flow, and browser E2E coverage.

## Core Principle

> ChatGPT may generate analysis. It may not directly create trusted state, official business decisions, or human approval.

The trust boundary remains unchanged:

```text
ChatGPT output
    -> UNTRUSTED IMPORT
    -> deterministic validation
    -> trusted intermediate artifact
    -> independent ChatGPT Judge pass
    -> UNTRUSTED JUDGE IMPORT
    -> deterministic decision engine
    -> trusted Executive Report
    -> human approval
    -> spec/design/plan
```

## Why Bridge Mode Is Two-Pass

The existing v0.3 architecture deliberately separates candidate generation from independent evaluation. A single ChatGPT conversation must not generate candidates and then act as its own independent judge.

Bridge Mode therefore uses two separate human-mediated ChatGPT passes:

1. **Forge Pass** — research, assumption breaking, mechanism transfer, ten candidate concepts, collision evidence.
2. **Judge Pass** — a fresh ChatGPT conversation that receives only validated evidence/candidate artifacts plus evaluation instructions. It does not receive the Forge model's preferred candidate, internal rationale, ranking, or recommendation.

The server creates the Judge package only after the Forge import passes deterministic validation.

This adds one manual handoff but preserves the Generator/Evaluator separation already enforced by PR D.

## Operating Modes

The application exposes two server-owned modes:

1. `chatgpt_plus_bridge` — default for the owner-operated zero-API-cost workflow.
2. `openai_api` — optional automation mode when `OPENAI_API_KEY` is configured.

The browser cannot select model IDs, provider URLs, secrets, system prompts, trusted verdicts, or internal validators.

The UI may let the user choose between supported modes only when the server declares them available.

## Readiness Semantics

### `/healthz`

Process liveness only.

```json
{"status":"ok"}
```

### `/readyz`

Application readiness means at least one supported execution path can complete an assessment workflow.

Bridge Mode requires no provider credential, so the deployed app can be ready without `OPENAI_API_KEY`.

Example response:

```json
{
  "status": "ready",
  "default_mode": "chatgpt_plus_bridge",
  "modes": {
    "chatgpt_plus_bridge": "ready",
    "openai_api": "not_configured"
  }
}
```

The previous `provider_not_configured -> 503` rule applies only to `openai_api` readiness and no longer makes the whole application unready when Bridge Mode is available.

## End-to-End Bridge Workflow

```text
1. User enters raw idea
2. App creates Forge request package
3. User runs Forge package in ChatGPT Plus
4. User imports Forge result
5. App validates evidence, assumptions, mechanisms, and exactly ten candidates
6. App creates Judge request package from validated artifacts only
7. User opens a fresh ChatGPT conversation and runs Judge package
8. User imports Judge result
9. App validates critiques and derives ten Reality Assessments
10. Deterministic Decision Engine derives GO/MODIFY/HOLD/KILL
11. Executive UX renders trusted result
12. Human approves GO/MODIFY only
13. Existing v0.2 handoff generates spec.md/design.md/plan.md
```

The application must never scrape `chatgpt.com`, automate the user login/session, extract ChatGPT cookies, or pretend that Plus is a server API.

## Bridge Session

A Bridge assessment is tracked by a server-generated `bridge_session_id`.

State machine:

```text
forge_requested
-> forge_imported
-> forge_validated
-> judge_requested
-> judge_imported
-> decision_ready
-> approved | blocked
```

Invalid imports do not advance the state.

The state machine must reject out-of-order operations such as Judge import before a validated Forge import.

## Forge Request Package

### Endpoint

`POST /api/bridge/forge-request`

Input:

```json
{"idea":"..."}
```

Only `idea` is client-controlled.

### Output Contract

The server creates a versioned Forge package containing at least:

```text
bridge_version
bridge_session_id
request_type = forge
created_at
raw_idea
objective
research_requirements
counter_evidence_requirements
assumption_requirements
transformation_vocabulary
mechanism_transfer_requirements
candidate_family_contract
required_output_schema
security_constraints
import_instructions
```

The package must require exactly the current ten candidate families:

1. adjacent_innovation
2. category_shift
3. zero_based_reinvention
4. axion_automation
5. prevention_shift_left
6. outcome_execution
7. workflow_infrastructure
8. data_decision_asset
9. buyer_revenue_inversion
10. compounding_asset

Each family must produce exactly one candidate.

The Forge package must instruct ChatGPT to:

- perform current web research when useful,
- seek evidence against the idea as well as for it,
- distinguish facts from hypotheses,
- preserve source URLs and source metadata rather than inventing them,
- extract and challenge assumptions,
- apply the approved transformation vocabulary,
- produce causal cross-industry mechanism transfers,
- generate exactly ten structurally different candidates,
- perform collision/prior-art/competitor/failure research,
- expose material unknowns and blockers,
- return only the requested result schema,
- not rank candidates,
- not choose a winner,
- not set Reality Verdicts,
- not set official GO/MODIFY/HOLD/KILL,
- not set human approval.

## Forge Result Import

### Endpoint

`POST /api/bridge/forge-import`

Accepted body contains exactly:

```text
bridge_session_id
bridge_version
result
```

The application rejects unknown top-level fields.

### Required Forge Result Domains

- evidence drafts / source metadata,
- assumption map,
- challenges and reframes,
- transformation results,
- mechanism transfers,
- exactly ten candidates,
- collision / contrary evidence findings,
- material unknowns,
- blockers,
- validation questions.

### Forge Admission Pipeline

```text
bridge envelope validation
-> session correlation validation
-> version validation
-> safe JSON size/depth/string limits
-> evidence normalization
-> evidence graph validation
-> assumption/reframe validation
-> mechanism validation
-> candidate contract validation
-> exact-ten-family validation
-> causal-chain validation
-> diversity validation
-> collision-request/result validation
-> trusted Forge Artifact persistence
```

A Forge import never creates the official business decision.

## Independent Judge Request Package

### Endpoint

`POST /api/bridge/judge-request`

Input contains only:

```json
{"bridge_session_id":"..."}
```

The server builds the Judge package from the validated Forge Artifact. The browser cannot supply or rewrite candidate/evidence content for the Judge package.

### Judge Context Minimization

The Judge package contains:

- original idea and baseline description,
- validated Evidence Graph summaries and claim IDs,
- validated ten candidate concepts,
- collision findings,
- material unknowns and blockers,
- evaluator dimension contract,
- required critique schema,
- instructions to perform additional current web research when material evidence is missing or stale.

The Judge package must exclude:

- any Forge preferred candidate,
- rankings,
- scores,
- generator self-critique presented as authoritative,
- official decision fields,
- human approval,
- hidden chain-of-thought or provider-internal reasoning.

The UI explicitly instructs the user to run the Judge package in a **fresh ChatGPT conversation** rather than the Forge conversation.

## Judge Result Import

### Endpoint

`POST /api/bridge/judge-import`

Accepted body contains exactly:

```text
bridge_session_id
bridge_version
result
```

The result must contain:

- baseline critique,
- exactly ten candidate critiques,
- all required evaluator dimensions,
- supporting/contradicting claim references,
- material unknowns,
- blockers,
- cheapest-next-validation suggestions,
- optional advisory `advance/revise/hold/reject` recommendations that remain untrusted.

The Judge import must not contain official GO/MODIFY/HOLD/KILL, confidence, selected candidate, or human approval fields.

## Judge Admission and Official Decision

```text
judge envelope validation
-> session/version validation
-> safe JSON limits
-> critique schema validation
-> target-ID validation
-> Evidence Graph reference validation
-> baseline + exact-ten critique coverage
-> blocker/unknown validation
-> deterministic Reality Assessment derivation
-> deterministic Decision Engine
-> final Executive Report validation
-> bounded AssessmentStore persistence
```

Only after this pipeline succeeds may the Bridge session become `decision_ready`.

## Evidence Integrity in Bridge Mode

Bridge Mode cannot cryptographically prove that ChatGPT truly visited every cited source. Therefore evidence admitted from Bridge Mode receives explicit provenance metadata:

```text
provider = chatgpt_plus_bridge
source_verification = user_mediated
```

A source URL must be syntactically valid and required metadata must be present. Missing publication dates, market definitions, geography, or other required fields are not fabricated by the server.

Claims that cannot satisfy the trusted Evidence Graph contract remain hypotheses/unknowns or cause the Forge import to be incomplete.

Judge-only newly discovered facts must be represented as evidence drafts with source metadata and pass the same Evidence Graph rules before a critique may rely on them for an official decision.

Bridge Mode must not silently lower existing market-size integrity rules.

## Official Decision Ownership

Official state remains server-owned:

```text
decision
confidence
selected_concept_id
human_decision
evolved_idea
```

Imported `recommendation`, `best_candidate`, `go`, `score`, or similar fields cannot set those values.

Only deterministic code can set decision/confidence/selected concept. Only the explicit human approval endpoint can set `human_decision`.

## Reality Evaluation

Every one of the ten candidate concepts must receive a server-derived Reality Assessment:

```text
ADVANCE
REVISE
HOLD
REJECT
```

Reality Assessment continues to use the existing evaluator dimensions and hard gates rather than a weighted total score.

The UI must show weak candidates rather than hiding them.

## Correlation, Expiry, and Replay Safety

Every Bridge session has a server-generated cryptographically unpredictable identifier.

Both imports require a known non-expired session ID and matching bridge version.

The Forge import can create one validated Forge Artifact. An identical replay returns the existing artifact reference; a conflicting second payload is rejected.

The Judge import follows the same idempotent-replay rule.

The Bridge registry is bounded and TTL-limited, following current AssessmentStore principles.

A server restart may lose pending Bridge sessions and assessment records. This limitation is acceptable for the owner-operated v0.3 pilot and must be visible in operations docs.

## UX

### Primary Bridge Path

```text
Idea input
-> "ChatGPT Plus로 분석"
-> Step 1: Forge package
-> Copy Prompt / Copy JSON / Download JSON
-> "새 ChatGPT 대화에서 Forge를 실행하세요"
-> Paste Forge Result / Upload JSON
-> Validate Forge
-> Step 2: Judge package
-> Copy Prompt / Copy JSON / Download JSON
-> "별도의 새 ChatGPT 대화에서 Judge를 실행하세요"
-> Paste Judge Result / Upload JSON
-> Validate Judge
-> Executive Decision
-> 10 Reality Cards
-> Evidence / Against / Unknowns
-> human approval
-> development package
```

The UI displays progress explicitly:

```text
1/4 Forge 준비
2/4 Forge 검증
3/4 독립 Judge 검증
4/4 공식 경영판단
```

### Optional API Path

When API mode is configured, a secondary control may expose `서버에서 자동 분석`.

When it is not configured, that control is hidden or marked unavailable. It must not make the application appear broken.

### Bridge Instructions

Both copyable ChatGPT instructions must be self-contained enough to run in new ChatGPT conversations. They must not contain server secrets or unnecessary private implementation details.

The UI states that imported ChatGPT output is revalidated by the app and is not itself the official verdict.

## Security

Bridge Mode must enforce:

- no API keys in browser payloads,
- no ChatGPT cookies/session extraction,
- no automated login or browser-session hijacking,
- no arbitrary URLs executed by the server from imported content,
- no HTML injection; render imported text with safe DOM APIs,
- JSON body-size limit,
- nesting-depth and collection-size limits,
- per-string length limits,
- exact schemas where practical,
- imported URLs treated as data only,
- no imported code execution,
- no imported filesystem paths or commands executed,
- no imported provider/model selection applied to server runtime,
- unpredictable session IDs,
- state-machine enforcement,
- idempotent replay handling,
- conflicting replay rejection,
- safe error messages without echoing full imported payloads.

## API Compatibility

Existing endpoints remain backward compatible:

- `/api/analyze`
- `/api/package`
- `/api/evolve`
- `/api/evolve/approve`
- `/healthz`

`/api/evolve` remains the API-backed automatic path and may return `PROVIDER_NOT_CONFIGURED` when API mode is unavailable.

New Bridge endpoints do not change those semantics except application-level `/readyz`, which becomes mode-aware.

## OpenAI API Adapter

Do not delete the current Responses API adapter, transport, live-provider smoke harness, or API-mode tests.

The adapter remains optional for future high-volume automation.

The server must not attempt to convert a ChatGPT Plus subscription into API authentication.

## Production Deployment

The current Render service remains usable without `OPENAI_API_KEY`.

After Bridge Mode deployment:

- `/healthz` must be 200,
- `/readyz` must be 200 because Bridge Mode is operational,
- the public root page must offer the Bridge workflow,
- API mode must truthfully report `not_configured` when no key exists,
- no provider secret is required for Bridge Mode.

## Browser E2E

Real Chromium E2E must cover at least:

1. create Forge request from an idea,
2. copy/export Forge package,
3. import a valid ten-candidate Forge fixture,
4. reject Forge result missing one family,
5. create Judge package only after validated Forge,
6. prove Judge package omits generator rankings/preference fields,
7. import valid baseline + ten-candidate Judge fixture,
8. render Executive Decision and ten Reality Cards,
9. GO human approval -> spec/design/plan,
10. MODIFY human approval -> evolved idea handoff,
11. HOLD -> approval blocked,
12. KILL -> approval blocked,
13. malformed import -> safe error,
14. wrong/expired session ID -> rejected,
15. out-of-order Judge import -> rejected,
16. duplicate identical import -> idempotent,
17. conflicting replay -> rejected,
18. XSS strings render as text,
19. API mode unavailable does not block Bridge Mode readiness.

E2E fixtures must be deterministic and must not depend on a live ChatGPT session.

## Verification Layers

The project keeps distinct evidence labels:

```text
DETERMINISTIC GREEN
BROWSER GREEN
DEPLOYMENT HEALTH GREEN
BRIDGE MODE GREEN
LIVE API PROVIDER GREEN   (optional; only when configured and smoke-tested)
PRODUCTION PILOT GREEN
```

Bridge Mode GREEN means Forge export/import + independent Judge export/import + deterministic decision + human approval + development package are all validated in production-equivalent tests.

It does not claim that every future ChatGPT-generated result will satisfy import validation.

## Production Pilot Definition

A real owner-operated production pilot is complete only when:

1. the public Render deployment is healthy and Bridge-ready,
2. an actual business idea is entered,
3. a real Forge request is generated,
4. the Forge request is run in the user's ChatGPT Plus session,
5. the real Forge result imports successfully,
6. a real Judge request is generated from the validated Forge Artifact,
7. the Judge request is run in a separate fresh ChatGPT conversation,
8. the real Judge result imports successfully or fails honestly with actionable validation errors,
9. ten candidate Reality Cards render,
10. an official deterministic GO/MODIFY/HOLD/KILL is derived,
11. if GO/MODIFY, the user explicitly approves,
12. spec/design/plan are generated successfully.

Only then may `PRODUCTION PILOT GREEN` be claimed.

## Failure Semantics

- Forge ChatGPT returns malformed result -> `bridge_forge_import_invalid`, no official verdict.
- Forge result misses a family -> rejected, no Judge request.
- Evidence contract cannot be satisfied -> Forge incomplete/rejected; no official verdict.
- Judge result malformed/incomplete -> `bridge_judge_import_invalid`, no official verdict.
- Judge references unknown candidate/claim -> rejected.
- Unknown/expired session -> rejected.
- Judge request before validated Forge -> rejected.
- Judge import before Judge request -> rejected.
- identical replay -> existing artifact returned.
- conflicting replay -> rejected.
- server restart loses pending session -> regenerate from the beginning; never infer trusted state.
- API mode unconfigured -> Bridge Mode still operational.
- imported text asks the server to ignore rules or execute commands -> treated as data and ignored.

## Out of Scope

- automating the user's ChatGPT login,
- scraping or controlling chatgpt.com,
- browser extension session capture,
- converting Plus billing into API credits,
- multi-user accounts,
- persistent database,
- billing/subscriptions,
- SaaS multi-tenancy,
- automatic background execution inside ChatGPT,
- guaranteeing unlimited Plus usage,
- a one-chat generator-and-judge shortcut.

## Acceptance Criteria

1. App is ready without `OPENAI_API_KEY` when Bridge Mode is enabled.
2. `/readyz` reports mode-level readiness truthfully.
3. User can create a versioned Forge package from only a raw idea.
4. Forge package is self-contained for a new ChatGPT conversation and contains no secrets.
5. Forge contract requires exactly ten candidate families and forbids generator ranking/winner fields.
6. Forge import is untrusted until deterministic validation completes.
7. A Judge package can be created only from a validated Forge Artifact.
8. Judge package omits generator preference/ranking and official decision fields.
9. UI instructs the user to execute Judge in a separate fresh ChatGPT conversation.
10. Judge import requires baseline plus exactly ten candidate critiques.
11. Invalid, oversized, malicious, partial, out-of-order, expired, or conflicting replay imports fail safely.
12. Existing Evidence Graph integrity rules remain enforced for Forge and Judge-discovered evidence.
13. Server derives exactly ten Reality Assessments.
14. Server alone derives official GO/MODIFY/HOLD/KILL, confidence, and selected concept.
15. Human approval remains required before development-package generation.
16. GO and MODIFY can hand off to v0.2 after explicit approval.
17. HOLD/KILL cannot generate development packages.
18. Existing API mode remains intact and optional.
19. Browser UI presents Bridge Mode as primary when API mode is unavailable.
20. Real Chromium E2E covers two-pass Bridge export/import/decision/approval/security paths.
21. Existing deterministic and browser regression gates remain GREEN.
22. Public Render deployment can reach `BRIDGE MODE GREEN` with no OpenAI API key.
23. `PRODUCTION PILOT GREEN` is withheld until one real two-pass ChatGPT Plus round-trip succeeds end-to-end.

## Success Definition

The feature succeeds when the owner can use an existing ChatGPT Plus subscription as a human-mediated two-pass intelligence layer while the Idea Vending Machine preserves independent evaluation and continues to enforce deterministic evidence, Reality Assessment, official decision, approval, and development handoff contracts without requiring OpenAI API spend.
