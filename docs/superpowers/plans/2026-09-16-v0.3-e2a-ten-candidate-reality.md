# v0.3 E2A Ten-Candidate Reality Evaluation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expand Candidate Forge from four to exactly ten mandatory business candidate families and derive an evidence-aware deterministic Reality Verdict for every candidate before the project-level decision engine runs.

**Architecture:** Provider creativity stays untrusted. Deterministic code creates candidate IDs, admits exactly one candidate per canonical family, enforces structural diversity and causal chains, consumes independent critiques, and derives `ADVANCE / REVISE / HOLD / REJECT` separately from `GO / MODIFY / HOLD / KILL`.

**Tech Stack:** Python 3.11 stdlib, unittest, existing Evidence Graph / Candidate Forge / Independent Evaluator / Decision Engine, GitHub Actions Production Gate.

**Spec:** `docs/superpowers/specs/2026-09-16-v0.3-e2-ten-candidate-executive-ux-design.md`

## Global Constraints

- Successful E2A runs create exactly ten candidates and exactly ten unique canonical families.
- No `non_applicable_families` escape hatch remains in E2A admission.
- Provider output cannot set candidate IDs, Reality Verdicts, confidence, selected concept, official decision, or human approval.
- Every candidate keeps explicit unknowns or validation questions and a complete causal value chain.
- Every candidate receives all ten existing independent-evaluation dimensions.
- Reality Verdict vocabulary is exactly `ADVANCE`, `REVISE`, `HOLD`, `REJECT`.
- Missing or contradictory decision-critical evidence is `HOLD`, never `REJECT`.
- Project-level `GO / MODIFY / HOLD / KILL` remains authoritative and separate.
- `/api/analyze`, `/api/package`, and E1 runtime failure semantics do not regress.
- No SaaS account system, database, billing, or client-controlled provider configuration.
